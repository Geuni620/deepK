## 평가 방법

표본·회차마다 두 출력을 무작위로 A/B에 배정한 평가지를 만들었다(`scripts/blind-quality-sheet.py`). 채점자 2명이 모델명을 모른 채 따로 채점했다.
- 메인 에이전트
- 별도의 독립 에이전트

출력마다 다음 세 가지를 매겼다.
- 중대 오류: 의미 반전, 누락, 숫자·코드 변경, 번역 대신 다른 내용 출력
- 만족한 checks 수
- 자연스러움(1~5)

표본마다 A/B/동률 선호도 함께 골랐다. 두 채점자 모두 Claude 모델이므로 사람 평가를 대체하지 않는다.

## 관찰

**Haiku 5.5가 나은 점**
- UI 문구: "can't be undone"을 '되돌릴 수 없습니다'로 번역했다. 4.5는 '취소할 수 없습니다'로 번역해, 취소 버튼과 헷갈릴 수 있다.
- 관용구: "hit the ground running"을 '제 몫을 해내고'로 의미에 맞게 번역했다.
- 반말 메신저: 'ㅋㅋ'를 'lol'로 바꿨다. 4.5는 'ㅋㅋ'를 그대로 남겼다.
- 숫자: '최대 2회까지 재시도'처럼 재시도 횟수가 분명하다.
- 영→한 긴 글: 4.5보다 덜 직역투이다.

**Haiku 5.5의 중대 오류: 영→한에서 영어 원문을 결과에 함께 출력**
- `en-long-1` 3회 중 2회: 문단마다 영어 원문과 한국어 번역을 번갈아 출력했다.
- `en-tone-1` 3회 중 1회: 영어 원문을 그대로 출력한 뒤 "Wait. Let me correct that. Here is the translation:"을 붙이고 번역을 이어 썼다.
- 세 건 모두 스트리밍 중간 결과와 최종 결과가 같아, 수집 과정이 아니라 모델 출력 자체의 문제다. 앱에서는 이 텍스트가 그대로 결과 창에 표시되고 복사된다.

**Haiku 4.5**
- 중대 오류는 없었다.
- 영→한 긴 글이 직역투이다(예: '완료를 측정하고, 첫 번째 단어가 나타날 때가 아닙니다').
- 고객 안내문 톤은 4.5가 더 낫다는 판정도 있었다.

**공통**
- 'All tests didn't pass'를 두 모델 모두 대부분 '모든 테스트가 통과하지 않아'로 번역했다. 부분 부정이 전체 부정으로도 읽힐 수 있다.

## 기본값 변경 판단

사전에 정한 기준과 비교했다.
- 중대 오류가 4.5 이하일 것: **미달** (3건 대 0건)
- 블라인드 선호에서 동률 이상일 것: 충족
- p50 지연이 20% 넘게 느리지 않을 것: 충족(19% 빠름)

위 기준만으로는 중대 오류 항목이 미달이었다. 원문을 함께 출력하는 실패는 사용자가 결과를 그대로 복사하는 앱 특성상 치명적이고, 영→한 장문에서 3회 중 2회 나왔으므로 우연으로 보기 어렵다.

**사용자 결정(2026-10-08)**: 더 빠르고 번역 품질도 낫다고 판단해 Haiku 5.5를 기본값으로 채택하고, Haiku 4.5는 선택지에서 뺐다. 이전에 Haiku 4.5를 저장한 사용자는 Haiku 5.5로 옮긴다. 원문을 함께 출력하는 실패는 남은 위험으로 추적한다.

## 프롬프트 보강 후 재측정 (2026-10-08)

원문을 섞어 내는 실패를 줄이려고 번역 프롬프트를 보강했다(`ClaudeTranslationClient.swift`).
- 시스템 프롬프트: "원문을 반복·인용하거나 번역과 번갈아 넣지 말고, 메모·정정·머리말을 붙이지 말 것"을 추가했다.
- 사용자 프롬프트: "Return only the translated text."를 "Return only the \<target\> translation; never include the \<source\> source text."로 바꿨다.

같은 표본·조건으로 Haiku 5.5를 다시 60회 쟀다. 모두 성공했다.
- 결과: [재측정](runs/20261008-haiku55-prompt-v2.json)
- 블라인드 비교: [보강 전후 비교](runs/20261008-haiku55-prompt-blind-review.json), 독립 에이전트 1명 채점

| | 보강 전 | 보강 후 |
| --- | ---: | ---: |
| 영어 원문을 섞어 낸 출력(기계 집계) | 3 / 60 | **0 / 60** |
| 중대 오류(블라인드 채점) | 3 | **1** |
| 자연스러움 | 4.63 | 4.70 |
| 블라인드 선호 승 / 패 / 동률 | 5 / 8 / 47 | 8 / 5 / 47 |
| 지연 p50 / p90 | 898 / 1,404 ms | 859 / 1,320 ms |
| 영→한 p50 / p90 | 908 / 1,492 ms | 910 / 1,320 ms |

기계 집계 규칙은 두 가지다.
- 영→한 출력에 25자 이상의 원문 문장이 그대로 들어 있는 경우
- 줄 맨 앞이 "Wait." 같은 머리말로 시작하는 경우

보강 전 결과에 이 규칙을 적용하면 사람(블라인드) 채점과 같은 3건이 나온다.

보강 후에도 남은 문제:
- `en-long-1#1`: 번역 앞에 "다음 텍스트를 한국어로 번역해 주세요:"라는 머리말이 붙었다. 지시문이 새어 나온 것으로 보이며 중대 오류로 판정됐다.
- `en-tone-1#3`: '궁금한 점이'의 '점'이 한자 '点'으로 나왔다. 채점자는 중대 오류로 보지 않았지만 결과에 그대로 보이는 결함이다.

판단: 원문 섞임이 사라지고 중대 오류가 3건에서 1건으로 줄었으며, 품질과 지연은 같거나 조금 나아서 보강을 유지한다. 머리말이나 한자가 섞이는 드문 실패는 남아 있다.

후속 후보:
- 결과 앞의 머리말이나 원문 문장, 대상 언어가 아닌 문자를 감지해 한 번 다시 요청하는 검증을 추가한다.

## 번역 출력 검사기 1단계 (2026-10-08)

프롬프트만으로는 출력을 보장할 수 없어, 결과를 규칙으로 검사하는 `DeepK/Translation/TranslationOutputLint.swift`를 만들었다. 앱 동작에는 아직 연결하지 않았다.

규칙:
- 원문 섞임
- 머리말
- 대상 언어가 아닌 문자
- 코드·자리표시자·URL 보존
- 문단 수와 길이 비율

오늘 출력 180개에 돌린 결과(`./scripts/lint-benchmark-outputs.sh`):

| 결과 파일 | 걸린 출력 | 내용 |
| --- | ---: | --- |
| Haiku 4.5 | 0 / 60 | (처음에는 영어 결과에 남은 'ㅋㅋ' 3건이 걸렸으나, 감정 표현은 허용하기로 해 제외) |
| Haiku 5.5 보강 전 | 3 / 60 | 원문 섞임 3건 |
| Haiku 5.5 보강 후 | 2 / 60 | 지시문 머리말 1건(제거 가능), 한자 '点' 1건 |

- 블라인드 채점에서 문제로 판정된 5건은 모두 탐지했다.
- 문제가 아닌 출력은 하나도 걸리지 않았다(오탐 0/175).
- 사용자 결정(2026-10-08)으로 자음·모음 단독 감정 표현('ㅋㅋ', 'ㅎㅎ', 'ㅠㅠ', 'ㄷㄷ' 등)은 영어 결과에 남아도 허용한다. 완성형 한글은 계속 위반으로 본다.
- 문자 단위 규칙은 예외가 계속 생길 수 있어, 원칙 기반 규칙으로 재설계하는 작업을 [issue #47](https://github.com/Geuni620/deepK/issues/47)에 정리했다.
- 앞으로 `benchmark-claude.sh` 결과에는 출력마다 `lintViolations`가, 표본 묶음마다 `lintFlagged`가 기록된다.

이 비교는 합성 표본 20개, 회차 3회의 소규모 검증이다.
