# 번역 파일럿 요약

실행일: 2026-09-19 08:19:50–08:22:39 UTC
경로: 유지된 Codex app-server stdio 프로세스 + 관리형 ChatGPT 로그인
CLI: `codex-cli 0.154.0`
요청: 10개 표본 × 3개 모델 = 30개, 모두 성공
제한: 요청·번역 각각 25초, `low` 추론 강도는 현재 client가 지원 목록에서 자동 선택
원시 결과: [`pilot-results.json`](pilot-results.json)

세 모델을 표본마다 순서를 회전해 실행했다. 각 `elapsedMs`는 현재 `CodexTranslationClient.translate()` 호출 전체 시간으로, 호출마다 수행되는 모델 목록 확인, ephemeral thread 준비, 도구 상태 확인, turn 완료, 최종 출력 수신을 포함한다. 클립보드·창 표시를 포함한 앱 전체 시간은 측정하지 않았다.

| 모델 | n | 최소 | 중앙값 | 평균 | 최대 | 1초 이내 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `gpt-5.6-luna` | 10 | 3,968 ms | 5,155 ms | 5,752 ms | 9,658 ms | 0/10 |
| `gpt-5.6-terra` | 10 | 3,952 ms | **4,681 ms** | **5,317 ms** | 8,721 ms | 0/10 |
| `gpt-5.6-sol` | 10 | 3,861 ms | 5,133 ms | 5,767 ms | 9,628 ms | 0/10 |

`gpt-5.6-terra`가 이 파일럿의 전체 client 시간 중앙값과 평균이 가장 낮아 **파일럿 범위의 후보**로 기록된다. n=10씩이고 방향·분량별 반복 측정이 충분하지 않으므로 p95를 계산하거나 최종 모델로 확정하지 않는다. 세 모델 모두 1초 이내에 완료된 호출이 없어, 이 결과로 앱의 1초 목표 달성을 주장할 수 없다.

## 품질 검토

실제 출력 30개를 `benchmarks/translation-samples.json`의 `checks`와 대조했다.

- 세 모델 모두 원래 창을 닫지 말라는 부정, 취소 뒤 응답 가능성, 최신 request ID 조건, 오래된 결과 복사 금지를 보존했다.
- 숫자 표본에서 `1.5초`, 최대 2회, `4,000자`와 `4,000바이트`를 보존했다.
- 코드 표본에서 `` `cancel()` ``, `` `requestID` ``, 세 줄 구조와 시간 초과의 부정 의미를 보존했다.
- 긴 표본에서 세 문단, 클립보드 실패 시 이전 값 전송 금지, 늦은 응답 무시, 전체 결과 표시 기준, 오류·시간 초과의 분리 기록을 보존했다.
- 중대한 의미 반전·누락·숫자 변경·코드 변경은 발견하지 않았다.
- `terra`의 영어 숫자 표본은 `최대 2회까지 시도합니다`로 번역되어 “재시도”가 명시적으로 반복되지는 않았다. 의미상 사용 가능하지만 다른 두 모델보다 표현이 모호한 경미한 품질 메모로 남긴다.

초기 제안 기준인 중대 오류 0건, 10개 중 8개 이상 사용 가능, 양방향 각 4개 이상은 세 모델 모두 통과한 것으로 기록한다. 이는 10개 표본의 파일럿 검토이며 최종 품질 검증이 아니다.

별도 유료 API 호출, 사용량 리셋, 리셋 크레딧 사용, 이메일·토큰 저장은 하지 않았다. 다음 단계는 준비 비용과 모델 응답 시간을 분리해 병목을 확인하는 것이다. 의미 있는 지연 개선 후에 구간별 반복 측정을 늘리고 앱 전체 경로를 검증한다. 현재의 미달 결과를 확인하기 위해 동일한 조건의 대량 호출을 먼저 반복하지 않는다.

재현 제한: 당시 클라이언트 파일의 해시는 별도로 기록하지 않았다. 측정 후 통신 캐시 정리·계측 코드가 변경될 수 있으므로 이후 실행은 새 결과 파일에 기록하고 이 파일럿과 구분한다.

## 후속 지연 분리 확인

동일한 짧은 문장으로 [지연 분리 기록](latency-breakdown.json)을 추가했다. 일반 계층의 5개 모델은 전체 약 4.15–5.71초, 준비 후 turn 응답은 약 3.66–5.11초였다. Luna·Terra·Sol의 Fast(priority) 계층도 각각 한 번만 시험했으며 전체 약 4.72–7.90초로 이번 표본에서는 개선되지 않았다. 이 소규모 후속 확인으로 Fast가 항상 느리다고 일반화하지 않는다. 앱 기본 계층은 바꾸지 않았다.

이 계측은 코드 준비 시간과 turn 완료 대기를 구분하며, turn 대기에는 서버·네트워크 시간이 포함된다. 순수 모델 생성 시간이나 실제 앱 전체 렌더링 시간으로 해석하지 않는다. 1초 목표는 여전히 미달이다.
