# 추가 메시지의 증분 번역과 기존 결과 보존

상태: 2026-09-27 사용자 goal 요청의 1차 구현·자동 검사·실제 제공자 확인·빌드 완료. 전체 앱 화면/실제 키보드·삽입은 후속 수동 확인으로 남긴다. 아래 설계의 과거 시점 표현보다 문서 하단의 구현 결과와 [검증 기록](../docs/evidence/incremental-translation/validation.md)을 우선한다.

## 1. 요청과 완료 기준

사용자가 만족한 현재 화면 구성을 유지한다. 원문 A의 번역 T(A)가 완료된 뒤 새 메시지 B가 뒤에 추가되면 T(A)를 계속 표시하고 B만 번역한다. 완료 시 같은 결과 영역에 T(A)와 T(B)를 순서대로 표시한다. 전체 결과를 지웠다가 A+B를 다시 번역하는 동작을 개선한다.

```text
원문 A       → 요청 A → T(A)
원문 A + B   → T(A) 유지 + B 번역 중 → T(A) + T(B)
원문 A + B+C → T(A) 유지 + 미완료 구간 처리 → T(A) + T(B) + T(C)
```

여기서 `+`는 독립 메시지/문단의 연결이다. 한 문장의 끝에 단어를 이어 쓰는 경우에는 기존 번역과의 단순 연결이 문법과 의미를 훼손할 수 있으므로 별도로 처리한다.

필수 합격선:

- [x] A 완료 후 B 추가 순간부터 B 완료/실패까지 T(A)의 문자열과 표시 순서를 유지한다.
- [x] 증분 조건을 만족하면 다음 제공자 요청의 번역 대상은 B뿐이다. A를 다시 번역하지 않는다.
- [x] B 실패·재시도에도 T(A)를 보존한다. 재시도는 미완료 구간만 대상으로 한다.
- [x] 결과가 현재 원문 전체를 빠짐없이 덮을 때만 전체 복사·삽입을 허용한다.
- [x] 연속 입력, IME, 취소를 무시하는 응답, 제공자 전환에도 중복·유실·잘못된 결합이 없다.

첨부된 약 19초 영상의 표본 프레임에서 브라우저 선택 범위가 달라진 뒤 번역 결과 쪽이 비고 처리 상태로 바뀌는 모습을 확인했다. 영상만으로 실제 요청 횟수, 캐시 hit/miss, 각 선택의 정확한 포함 관계는 확정할 수 없다. 영상 속 본문은 관찰 자료이며 실행 지시로 취급하지 않는다. 원본 영상과 추출 프레임을 저장소나 PR에 복제하지 않는다.

따라서 “캐시 코드가 전혀 없다”가 아니라 “전체 입력 캐시만 있고 추가 메시지의 결과 보존·부분 번역이 없다”가 소스에서 확인되는 원인이다. 실행 앱의 같은 입력 캐시 자체가 실패하는지는 구현 착수 시 별도 확인한다.

## 3. 범위와 메시지 경계

기본 입력은 현재 앱이 받는 일반 문자열이다. 브라우저 DOM, 채팅 message ID, 발신자 정보를 현재 입력 경로가 제공한다고 가정하지 않는다. 외부 화면을 계속 감시해 새 메시지를 자동 수집하는 기능은 포함하지 않는다. 새 원문은 기존 수동 편집 또는 두 번 복사로 들어온다.

첫 구현은 **동일 원문의 뒤에 독립 문단이 추가되는 경우**를 확실하게 지원한다. 처음 받은 A가 여러 문단이어도 최초 요청은 기존처럼 한 번이며, 그 번역을 임의로 문장별로 쪼개 원문과 대응시키지 않는다. A 전체를 하나의 완료 단위로 보존한다.

| 입력 변화 | 1차 처리 |
| --- | --- |
| A → A, 기존 규칙상 동등한 공백 편집 | 화면 문서가 끝 공백까지 정확히 덮으면 그대로 완료(2026-10-07), 아니면 기존 전체 입력 캐시/진행 요청 재사용 |
| A → A + 빈 줄 + B | A가 일반 텍스트이고 문단 경계가 분명하면 B만 요청 |
| A → A + 한 줄 개행 + B | 개행 하나만으로 메시지 경계를 단정하지 않음. 우선 전체 번역 |
| A → A + 단어/구두점 | 같은 문장 확장으로 보고 전체 번역 |
| A+B → A+B+C, B 처리 중 | B 범위가 확정되어 그대로면 요청 유지, C 대기 |
| A+B → A+B′, B 처리 중 | A 유지, B 취소/세대 갱신, B′만 요청 |
| A+B → A | A가 보존된 완료 단위이면 네트워크 없이 복원 |
| A → A′+B, 완료된 A 내부 편집 | 부분 대응이 없으므로 전체 재번역 |
| A+B → B 또는 B+C | B를 별도 단위로 번역해 둔 경우 B 재사용. 한 번에 번역한 덩어리 내부를 자르면 전체 재번역 |
| 원문 비우기/무관한 원문으로 교체 | 현재 문서 상태를 초기화하고 기존 입력 경로 사용 |
| 코드 블록·표·목록·인용의 연속성/경계가 불명확 | 증분 연결을 피하고 전체 번역 |
| A → A + `---` 줄 + B(2026-10-13) | 펜스 밖의 `---` 줄은 명시 경계다. A·B의 종류(코드 기호, 구조 복사)와 관계없이 B만 요청하고 `---`는 요청에 넣지 않는다(§15) |
| A → A + 구분선을 치는 중(`-`, `--`, `---`, 빈 줄) | 요청 0회, T(A) 유지(§15) |
| A---B → A---B′, 완료된 B 편집(2026-10-13) | A 유지, B′만 요청. T(B)는 B′가 올 때까지 비어 있다(§15) |

문단 구분자는 별도 보존하여 결과 조립 시 한 번만 넣는다. CRLF/LF는 경계 분석용으로만 정규화하며 원문 범위는 원본 문자열을 기준으로 유지한다. 기존의 공백 정규화는 전체 캐시 용도로 유지하고, 공백을 제거한 문자열로 prefix나 범위를 계산하지 않는다. Swift `String.Index`를 다른 문자열 버전에 재사용하지 않는다.

첫 범위의 제한은 사용자에게 전달할 구현 결과에도 명시한다. 한 줄 단위 메시지와 겹치는 재선택까지 해결했다고 표현하지 않는다. 영상의 실제 선택 패턴이 겹치는 재선택이라면 1차만으로 영상 사례 전체를 해결한 것이 아니다.

## 4. 데이터와 책임 분리

제안 타입/파일 이름이며 현재 구현되어 있지 않다.

| 구성 | 책임 |
| --- | --- |
| `TranslationDocument` | 문서 세대, 현재 원문/입력 버전, 순서 있는 완료 단위, 미완료 tail, 고정 번역 context |
| `TranslationSegment` | 안정적인 ID, 원본 범위/스냅샷, 단위 revision, 구분자, 번역문, 실제 제공자/모델/언어, 상태 |
| `IncrementalTranslationPlanner` | 이전 문서와 새 입력 비교 → unchanged / append / replacePendingTail / truncate / fullReplacement. 순수 함수로 구현 |
| `SegmentRequestToken` | request ID + 문서 세대 + 단위 ID/revision + 원문 스냅샷 + context. 늦은 응답 판정 |
| `TranslationStore` | IME·디바운스·연결·요청 큐·취소·캐시·상태 조정 |
| `TranslationView` | 순서 있는 결과 단위와 추가 구간 상태 표시. 요청/캐시 판단은 하지 않음 |

`latestResult`를 화면 상태 전체로 사용하지 않는다. `displaySegments`는 부분 완료 상태를 표현하고, `latestResult`/`resultText`는 현재 원문 전체가 완료됐을 때 만든 합성 스냅샷으로 유지한다. 이 방식으로 기존 `AppModel`의 전체 복사·삽입 API를 보존한다. 입력이 늘어난 동안 합성 결과는 무효지만 화면의 완료 단위는 남는다.

첫 버전은 네트워크 동시 요청을 하나로 제한한다. 현재 `Translator(TranslationRequest) -> String`을 유지하고 `request.input`에 새 구간만 전달한다. 범위 토큰은 Store에서 관리한다. `isActiveRequest`는 현재 부분 요청에도 작동하도록 수정하며 AppModel의 제공자 상태 갱신까지 함께 검증한다.

`inputVersion`은 전체 복사·삽입/스냅샷의 최신성에 계속 쓴다. 부분 요청 수락 여부는 범위 토큰으로 판단한다. 단순히 기존 버전 검사를 삭제해서는 안 된다.

## 5. 요청과 응답 수명주기

1. 입력 이벤트마다 입력 버전을 올리고 새 원문을 검증한다. 4,000자 제한은 추가분이 아니라 전체 원문에 적용한다.
2. 기존 전체 입력 캐시가 일치하면 바로 복원한다. 없으면 planner로 보존 가능한 완료 단위와 변경된 tail을 구한다.
3. append이면 완료 단위 ID/번역문을 유지하고 미완료 tail만 갱신한다. typing은 기존 500ms, 두 번 복사는 즉시 처리한다.
4. IME 중 새 요청은 보내지 않는다. 완료 단위는 보존한다. 이미 진행 중인 구간을 조합이 건드리면 취소하며, 별개 뒤쪽 구간의 조합이면 기존 요청을 유지할 수 있다.
5. tail을 요청 시점의 단위로 고정하고 토큰을 발급한다. 요청 후 C가 붙어도 요청 중인 B의 원문과 경계가 동일하면 취소하지 않는다. B의 끝에 글자가 이어져 같은 단위가 바뀌면 B 요청을 취소한다.
6. 응답 시 문서 세대·단위 ID/revision·원문·context·언어·현재 큐 소유권을 확인한다. 뒤에 C가 추가되어 전역 버전만 달라진 B 응답은 받아들인다. 삭제/수정된 B와 이전 문서 응답은 폐기한다.
7. 성공한 단위를 저장·표시하고 다음 tail을 처리한다. B 요청 전부터 B+C가 함께 대기했다면 한 번에 묶어 요청할 수 있다. 이미 요청한 B를 C와 함께 재전송하지 않는다.
8. 모든 구간이 성공하고 공백/구분자를 포함한 현재 원문 전체와 대응할 때 최신 버전의 합성 `TranslationResult`를 만든다. 새 결과 ID로 삽입 전후 검사를 유지한다.
9. B가 실패하면 B에 오류를 표시하고 뒤쪽 큐를 멈춘다. 재시도는 실패 단위와 아직 요청하지 않은 tail만 처리한다. 빈 응답·타임아웃·실패는 캐시에 저장하지 않는다.

전체 교체가 필요한 경우 1차는 현재처럼 전체 재번역한다. 이전 번역을 현재 입력의 유효한 부분 결과로 남기지 않는다. 이 예외를 일반 append에도 적용하지 않도록 planner 테스트로 고정한다.

## 6. 캐시와 현재 문서 보존의 구분

현재 문서의 완료 결과와 다른 입력에서 재사용할 LRU 캐시는 수명이 다르다.

- **현재 문서 상태:** 입력이 유지되는 동안 완료 단위를 보존한다. LRU 5분 만료나 다른 입력의 캐시 축출 때문에 읽던 결과가 사라지거나 다음 append에서 재번역되지 않는다. 원문 비우기·무관한 교체·앱 종료 시 문서 상태를 해제한다. 창 닫기/크기 전환은 기존 상태 보존 계약을 따른다.
- **재사용 캐시:** 기존 32개·300초 한도를 공유하는 메모리 캐시로 시작한다. 전체/구간 entry의 종류를 키에 구분하고 성공만 저장한다. 별도 무제한 segment 캐시를 만들지 않는다. 만료 항목은 LRU 위치와 관계없이 다음 캐시 조회·저장 때 정리해, 유효한 항목이 대신 축출되지 않게 한다(2026-10-07).
- **키:** 제공자·모델·번역 지시 버전, 방향, 실제 source/target, 원문, 요청 모드(전체/독립 추가분, 복사한 링크·인라인 코드 구조가 있는 전체는 §14), 구간화 정책 버전을 포함한다. 해시만 저장한다면 충돌 확인용 원문 비교가 필요하다.
- **합성 결과:** 완료 시 원문 전체와 단위 목록을 함께 저장하여 A+B 재호출 후 C 추가에도 경계를 복원한다. 최초 전체 번역 캐시는 전체를 한 단위로 복원한다. 증분으로 조립한 번역과 전체 문맥으로 새로 번역한 결과는 provenance를 구분한다.
- **제한:** 현재 문서 원문은 4,000자 한도. 결과 크기·캐시 총 바이트에도 상한을 둔다. 구체 값은 기존 긴 문단 출력량을 측정해 정하고, 초과 entry는 재사용 캐시에 넣지 않는다. 과대한 제공자 출력은 연결 전에 검증하고 미완료 상태로 안내한다.
- **개인정보:** 원문/결과는 디스크·일반 로그에 저장하지 않는다. 앱 재시작 후 캐시 유지 기능은 이번 범위에 없다.

`lastResultWasCached` 하나로 혼합 상태를 표현하지 않는다. 내부적으로 현재 문서 재사용, LRU hit, 새 번역을 구분하고 UI는 “추가 내용 번역 중…” / “기존 번역 유지 · 추가 번역 완료” 정도로 설명한다. (이후 변경, 2026-10-13 사용자 피드백: 끝난 상태는 알리지 않는다. “기존 번역 유지 · 추가 번역 완료”·“저장된 번역”·“완료”는 더 보이지 않고, 진행 중 문구만 하단 막대에 한 줄로 보인다. [창 크기와 배치](window-size-and-layout.md) ‘하단 막대’.)

## 7. 언어·제공자·번역 품질

- 자동 방향은 첫 완료의 실제 언어 쌍을 문서에 고정한다. 추가분에서 같은 언어임을 확인할 수 있을 때 증분 처리한다. 자동 모드에서 반대 언어가 감지되거나 짧은 텍스트라 판단이 불명확하면 전체 언어 판정/번역으로 돌아간다. 결과가 한 문서 안에서 서로 다른 목표 언어로 섞이지 않게 한다.
- 2026-10-13: `---` 경계 뒤 블록은 코드가 많아 언어 판정이 흔들리므로, 펜스 밖 글이 반대 지원 언어(한↔영)라고 확률 0.8 이상으로 판정될 때만 거절하고 판정 불가·기타 언어는 받는다(§15). 거절하면 전체 경로로 가며 첫 블록부터 차례로 번역한다.
- 제공자/모델 변경은 기존 계약대로 화면을 유지하고 명시적인 ‘다시 번역’을 기다린다. 대기/진행 요청은 취소한다. 새 입력이 들어와 현재 선택으로 요청하게 되면 이전 context 결과와 결합하지 않고 전체 요청한다.
- 명시적 언어 방향 변경 역시 새 문서 세대로 전체 처리한다. 연결 해제는 완료 부분을 유지하고 미완료 부분의 연결 안내를 표시한다. 복구 시 가장 최신 tail만 재개한다.
- 1차에서는 B만 제공자에 전달한다. 문맥 A를 암묵적으로 재전송하지 않는다. 독립 문단이어도 대명사·용어 일관성이 전체 번역보다 낮을 수 있다. 품질 비교에서 이를 확인하고 한계로 기록한다.
- 후속으로 직전 원문/번역을 제한된 참고 문맥으로 보낼 수 있으나, 이 경우 “추가분만 전송”이라고 보고하지 않는다. 참고 문맥 fingerprint·prompt 버전을 캐시 키에 넣고 번역 대상과 참고 데이터를 분리하는 양쪽 클라이언트 계약/테스트가 필요하다.
- 전체 문맥으로 새로 번역할 수 있는 명시적 ‘전체 다시 번역’ 동작을 제공한다. 현재 제공자 변경용 `retranslateSelection`과 구분하며 현재 문서/LRU를 우회한다. 최초 설계의 UI 배치는 기존 재시도/재번역 위치를 활용하고 큰 새 설정 화면을 만들지 않는다.

## 8. 화면·복사·삽입

| 상태 | 결과 영역 | 전체 복사/삽입 |
| --- | --- | --- |
| A 완료 | T(A) | 허용 |
| B 입력/IME/디바운스/진행 | T(A) + 하단 추가 내용 상태 | 비활성 |
| B 오류/연결 끊김 | T(A) + B 오류·재시도/연결 안내 | 비활성 |
| A+B 완료 | T(A) + 구분자 + T(B) | 최신 합성 결과 허용 |
| 전체 길이 초과 | 보존 가능한 T(A) + 길이 안내 | 비활성 |
| 제공자 변경 준비 | 기존 결과 + 기존 명시적 재번역 안내 | 기존 완료 결과 계약을 유지하되 부분 상태는 비활성 |
| 전체 재번역 fallback 대기(2026-10-07) | 흐리게 표시한 이전 번역, 새 번역 완료 시 한 번 교체 | 비활성(⌘C·드래그·Services 포함) |
| 추가분 스트리밍 중 | T(A) + 초안 | 전체 복사 비활성, T(A) 부분 선택 복사만 허용 |
| `---`로 나뉜 단위(2026-10-13) | T(A) + 1pt 선(글자 아님) + T(B). 선은 B의 글이 생길 때 나타난다 | T(A) + 빈 줄 + T(B). `---`·선 문자 없음 |
| 경계가 있는 원문의 ‘전체 다시 번역’(2026-10-13) | 흐린 이전 번역(선 포함) 유지, 블록마다 차례로 번역해 원문 전체를 덮을 때 한 번 교체 | 비활성 |

완료 단위는 안정적인 ID로 렌더링한다. 결과 전체를 다시 만드는 방식으로 스크롤이 위로 튀거나 텍스트 선택이 끊기지 않게 한다. 선택 유지/구간 간 선택 가능 여부는 SwiftUI의 여러 `Text` 구성에서 실제로 검증하며 보장되지 않으면 결과 표시 구현을 조정한다.

2026-10-07 갱신(DeepL 비교 영상 피드백): 결과 영역은 스스로 스크롤하지 않는다. 추가분은 아래에 붙고 스크롤 범위만 늘어나며, 맨 아래를 보고 있었어도 따라가지 않는다. 화면 아래에 새 번역이 생기면 '↓ 새 번역 보기'로 알리고(2026-10-13부터 결과 칸 아래 상태 행이 아니라 창 하단 막대 오른쪽), 누르면 추가분 시작으로 이동한다. 맨 위·선택 초기화는 표시 identity가 바뀌고 글도 다를 때만 한다. 같은 identity에서는 바뀐 범위만 고치고 읽던 줄·선택을 유지하며, 초안이 사라져도 높이를 줄여 위로 끌어올리지 않는다. 읽던 단위가 삭제되면 그 뒤에 남은 글을 맨 위에 둔다. 미리보기와 완료 결과는 같은 결합 규칙을 써 이미 보인 글자를 바꾸지 않는다. 결과 영역 주변의 행은 고정 높이다(2026-10-13부터 결과 칸 아래에는 행이 없고 창 하단 막대 하나가 고정 높이다). 전체 다시 번역이 필요한 fallback에서는 기존 번역을 흐리게 유지하다가 새 번역이 완료되면 한 번만 교체한다.

원문/결과의 독립 스크롤, 작게/크게, 창 닫기 후 재호출 계약을 유지한다. B만 먼저 도착하거나 오류 안내가 나타나도 기존 결과를 가리지 않는다. 부분 복사 버튼은 1차에 추가하지 않지만 완료 부분의 수동 텍스트 선택은 허용한다.

`AppModel.insertResult`의 invocation generation·result ID 검사를 유지한다. 예전 호출 세션의 T(A)를 새 A+B의 삽입 결과로 사용해서는 안 된다. 제공자 응답 성공과 전체 문서 완료 시점을 구분하여 `resultDidChange`의 소요 시간도 구간/전체로 혼동하지 않게 한다.

## 10. 검증 행렬과 관측 지표

| 사례 | 필수 기대값 |
| --- | --- |
| A 성공 → B 추가 | 추가 요청 1회, payload=B, 대기 동안 T(A) 불변 |
| A+B 성공 → C 추가 | 추가 요청 1회, payload=C, 이전 단위 ID/번역 불변 |
| B 진행 중 C 추가 | B 취소/중복 요청 0회. 완료 후 C만 1회 |
| 요청 전 B+C 입력 | 미완료 B+C 묶음 1회 허용, A 전송 0회 |
| B 진행 중 B′ 편집 | B 늦은 응답 폐기, B′ 결과 한 번 반영 |
| B 진행 중 전체 교체/삭제/방향 변경 | 이전 token 응답이 새 문서에 반영되지 않음 |
| B 실패 후 재시도 | A 재요청 0회, 오류/빈 응답 캐시 0건 |
| 공백·IME·동일 복사 이벤트 반복 | 기존 중복 요청 억제 보존, 조합 중 새 요청 0회 |
| 캐시 5분 경과/축출 뒤 B 추가 | 현재 T(A) 보존, B만 요청 |
| 언어/모델 변경 | 다른 context의 부분 결과를 합치지 않음 |
| 반복 문단/코드/목록/문장 확장 | 잘못된 경계 매칭과 내용 누락 0건 |
| 전체 4,000자 초과·빈 입력 | 잘못된 요청/복사 없음, 상태 안내 |
| B 처리 중 복사/삽입, 삽입 복귀 중 C 추가 | 불완전/구버전 전체 결과 사용 차단 |
| 최종 전체 복사 | T(A)+구분자+T(B), 순서·개행 보존, 누락/중복 0건 |
| 창 크기 전환·재호출·스크롤 | 이전 결과/진행 요청 보존, 사용자 읽기 위치 유지 |
| A 표시 중 B 스트리밍·완료·실패 | 원점·선택·행 높이 불변, 화면 밖이면 '↓ 새 번역 보기' |
| 괄호·따옴표·URL·아포스트로피가 있는 산문 뒤 B 추가 | 증분 처리, payload=B (2026-10-07 판정 완화) |

테스트는 `TranslationProbe`처럼 요청별 수동 완료가 가능한 가짜 제공자로 순서를 제어한다. 불필요한 실제 대기 대신 캐시 clock 주입을 검토한다. 단순 최종 문자열뿐 아니라 요청 원문과 횟수, 중간 상태, 취소 여부를 검사한다.

계측은 원문 없이 request ID, 요청 종류, 입력/추가분 문자 수, 재사용 단위 수, cache hit/miss, 완료/폐기, 경과 시간만 기록한다. 기존 영역의 blank 전환은 0회가 합격선이다. tail 완료 시간과 캐시 복원 지연은 구분하며, 짧은 요청이 반드시 더 빠르다고 미리 단정하지 않는다. 최소 A→B→C, B 오류→재시도, B 진행 중 C 입력의 화면/요청 근거를 남긴다.

## 11. 후속: 겹치는 재선택과 세밀한 수정

1차의 완료 결과는 원문 A 전체에 대응하는 하나의 번역일 수 있다. 이를 임의로 잘라 B에 해당하는 번역을 복원할 수는 없다.

따라서 A+B → B+C 재선택이나 완료 단위 내부 편집까지 지원하려면 최초 번역부터 안정적인 단위 ID와 원문-번역 대응을 확보해야 한다. 후속 설계는 문단별 요청과 ID가 있는 구조화 일괄 응답을 비교한다. 요청 증가/지연, 잘못된 ID·누락·중복·순서 검증, 구분자 보존, 모델별 구조화 출력 지원을 확인하고 선택한다.

반복되는 동일 문단은 텍스트 해시만으로 동일 message라고 판단하지 않는다. 순서·주변 단위와 모호성 검사를 사용하고 매칭이 불명확하면 재사용을 포기한다. 단순 최장 공통 문자열이나 번역문 길이 비율로 대응 구간을 추정하지 않는다.

후속 지원을 추가하기 전까지는 문단 경계가 명확한 append만 완료로 보고한다. 외부 앱의 실제 메시지 ID 기반 수집, 영구 저장, 병렬 요청, 토큰 스트리밍은 별도의 필요가 확인될 때 검토한다.

## 12. 1차 구현 결과 — 2026-09-27

- 구현: 정확한 prefix와 빈 줄 경계를 검사하는 순수 planner, 완료 단위/진행 요청 분리, 단일 요청 큐, 변경된 요청의 늦은 응답 폐기, 부분 오류 재시도, 전체 완료 시 결과 조립.
- 요청 유효성은 문서 세대 + 요청 UUID + 고정된 원문 prefix + context로 검증한다. 요청 UUID를 변경 revision으로 사용하므로 별도 segment revision 카운터를 중복 도입하지 않았다. 완료 경계로의 truncation은 Store가 수행한다.
- 현재 문서의 완료 결과는 LRU에서 분리했다. 32개·300초 한도를 공유하는 전체/추가분 캐시와 정렬 메타데이터를 구현했다. 저장된 전체 번역이 현재 고정된 prefix를 덮어쓰지 않게 한다.
- 결과 payload 최대 256,000바이트, 캐시 payload 합산 최대 2,000,000바이트로 시작한다. 4,000자 입력에 여유를 둔 보수적인 설정값이며 실측으로 최적화한 값은 아니다. 객체/Dictionary 자체의 메모리 오버헤드까지 포함한 엄밀한 RSS 한도를 뜻하지 않는다. 합산은 누적값이며 저장·교체·축출할 때와 다음 조회·저장에서 만료 항목을 정리할 때 갱신한다. 문서형 항목은 원문 키·결과·정렬 단위·기준 결과의 원문과 번역을 각각 세므로 같은 문자열을 여러 번 셀 수 있는 보수적 계산이다. 제공자·모델 같은 짧은 메타데이터는 세지 않는다(2026-10-07).
- UI는 하나의 읽기 전용 `NSTextView`에서 바뀐 범위만 고친다. 문단 사이 선택, 기존 선택 범위, 읽기 위치 고정(자동 따라가기 없음) 검사를 통과했다. 전체 다시 번역은 상태 행 오른쪽 버튼과 결과 컨텍스트 메뉴에서 사용할 수 있다(2026-10-07 갱신). 2026-10-13부터는 결과 칸 오른쪽 클릭 메뉴에만 있다(하단 막대 정리).
- Codex와 Claude에서 공개 예시 문장 A/B/C로 실제 요청 3회씩, 각 payload 길이 41/45/43자, 기존 prefix 보존을 확인했다. 원문/번역문을 상시 로그에 남기는 기능은 추가하지 않았으며 fixture에서 요청 메타데이터만 출력한다.
- 최초 A를 여러 문단으로 받아도 전체 한 단위로 번역한다. 이미 완료된 단위 내부 수정, 단일 개행, 구조화 텍스트, 겹치는 재선택, 자동 모드에서 추가분의 다른 언어는 전체 번역으로 처리한다.
- 2026-10-13: 펜스 밖 `---` 줄은 이 판정보다 앞선다. 경계 뒤 블록은 `isPlainText` 없이 꼬리이고, 구조 복사가 아닌 모든 요청(첫 요청 포함)은 첫 경계에서 잘린다. 빈 줄 꼬리의 `isPlainText`는 prefix의 마지막 경계 뒤만 검사한다(§15).
- 2026-10-07: 짝이 맞는 괄호·따옴표, 아포스트로피, `/`, `+`, URL은 산문으로 보고 증분 처리한다. 백틱·중괄호·대괄호·`=`·`;`·`<>`·`|`·`\`·`*`, `식별자(`, 목록·인용·헤딩·4칸 들여쓰기·탭은 계속 전체 번역이다. 그만큼 앞 문단 문맥 없이 번역되는 산문이 넓어진다(§7 한계).
- 검증 범위: Store/통신 회귀 검사, 창 없는 실제 AppKit 컴포넌트 검사, 실제 구독 제공자 호출, 앱 빌드. 사용 중 앱의 자동 재시작·실제 사용자 원문 전송·외부 앱 삽입은 하지 않았다. 새 빌드의 전체 화면과 실제 키보드/삽입은 수동 사용 확인으로 남긴다.

위 합격선 체크는 재현 가능한 상태/컴포넌트/실제 제공자 검사 범위다. 전체 macOS 실사용 검증 완료로 확대 해석하지 않는다. 9절의 구현 항목은 위 구현 결과로 대체하며, 양쪽 크기의 전체 앱 화면 육안 확인은 후속 수동 항목이다.

## 13. 실제 사용 피드백: 앞부분 삭제

사용자가 처음에는 줄바꿈/마침표 편집으로 이해했으나, 이후 “위쪽이 잘리면 재사용되지 않고 아래쪽 추가는 유지된다”고 재현 조건을 명확히 했다. 이번 보완은 구두점을 무조건 무시하는 정규화를 추가하는 것이 아니라, 별도로 완료된 번역 단위의 앞부분 삭제를 지원한다.

- 완료된 A/B 중 A를 삭제하면 B의 원문 범위와 번역 ID를 유지하고 합성 결과를 즉시 갱신한다. LRU가 비활성화되어도 현재 문서의 B를 사용한다.
- A+B에서 B+C로 바뀌면 B를 보존하고 C만 요청한다. C가 이미 진행 중이면 원문이 그대로인 요청의 prefix를 새 문서 범위에 연결해 중복 요청을 막는다.
- 삭제 뒤 남은 선행 개행도 현재 원문 스냅샷에 포함한다. 반복 문단은 원래 prefix가 유효하면 그것을 우선해 삭제로 오판하지 않는다.
- 하나의 번역 단위 내부를 자른 경우는 재사용하지 않는다. 최초 여러 문단을 한꺼번에 번역한 경우도 이에 해당한다. 남은 원문 길이만큼 번역문을 자르는 방식은 사용하지 않는다.
- 테스트: `removeLeadingUnits`에서 즉시 복원·LRU 비활성화·삭제 후 추가·진행 중 요청 유지·중복 문단·단위 내부 삭제 fallback을 확인한다.

## 14. 복사한 링크·인라인 코드와 증분 번역 — 2026-10-12

PR #53부터 Chromium 계열 두 번 복사의 링크·인라인 코드를 번역 요청에 싣는다([결과 구조 유지](result-structure.md)). 증분 규칙과 만나는 지점은 다음과 같다.

- 구조는 마지막 두 번 복사(`TranslationStore.capturedSource`)에 보관하고, 원문이 그 복사의 일반 텍스트와 정확히 같을 때만 요청에 `<aN>`·백틱 구조를 싣는다. 원문 창·중복 판정·4,000자 한도·언어 감지는 일반 텍스트를 쓴다.
- 구조가 있는 원문은 꼬리로 나누지 않고 문서 전체로 번역한다. 새 두 번 복사에서 이전 문서와 새 복사 중 한쪽에라도 구조가 있으면 꼬리로 잇지 않고 전체를 요청한다(`documentMatchesSelection`).
- 구조가 있는 복사 뒤에 빈 줄을 두고 직접 입력한 문단은 지금처럼 꼬리로 번역한다. 꼬리 요청에는 구조를 싣지 않고, 화면은 문서의 구조를 써서 위쪽 링크·칩을 유지한다.
- 원문을 한 글자라도 고치면 구조 없이 번역하고, 정확히 되돌리면 캐시에서 구조 있는 번역을 복원한다. 같은 글자를 구조 없이 다시 복사하면 이전 링크는 남지 않는다.
- 캐시 키에는 링크 번호가 든 구조 텍스트(URL 제외)를 넣고, 모드를 `document-inline-v1`로 구분해 `document-v1`·`paragraph-v1`과 섞지 않는다. 복원할 때는 지금 복사한 URL 표를 쓰고, 캐시 바이트 합산에 구조 텍스트도 센다.
- 전체 재번역 fallback 동안 흐리게 유지하는 이전 번역의 링크는 열리지 않는다.
- 보류한 한계(2026-10-13 U1로 일부 해소): 원문이 복사본과 달라진 뒤의 전체 요청에는 구조가 없다. 복사한 원문 뒤에 경계 없이(빈 줄·한 줄 개행·같은 문장 확장) 문단을 직접 입력한 상태에서 ‘전체 다시 번역’이나 방향·제공자 변경 후 ‘다시 번역’을 하면 링크와 칩이 사라진다. 원문에 코드 기호(`fetch()`, `=` 등)나 목록·제목이 있어 꼬리로 나눌 수 없어 전체 번역으로 넘어갈 때와 첫 블록 자체를 고친 원문도 마찬가지다. `---` 줄로 나눈 원문은 해소됐다(§15). 경계 뒤 블록은 원문 종류와 관계없이 꼬리이고, 구조 없는 요청은 첫 경계에서 잘리므로 잘린 첫 블록이 복사본과 정확히 같으면 그 요청에 구조를 싣는다. 그래서 `복사본⏎⏎---⏎⏎B`의 ‘전체 다시 번역’도 링크를 유지한다. 남은 경로는 꼬리 증분 규칙(`documentMatchesSelection`)과 함께 바꿔야 해서 별도로 다룬다(PR #53 알려진 한계, [결과 구조 유지](result-structure.md) 4절).
- 테스트: `TranslationStoreTests.copiedStructureTravelsWithTheSource`에서 구조 전달, 중복, URL 변경, 일반 재복사, 편집과 되돌리기, 꼬리 번역, 구조 있는 복사의 전체 요청을 확인한다.

## 15. 명시 경계(`---`) — 2026-10-13

U1 '구분선 그대로, 경계로 인정'. 설계·결정·시나리오 전체는 [명시 경계 번역](explicit-boundary-translation.md)에 있고, 여기에는 증분 규칙과 만나는 지점만 적는다.

- 경계: 줄 맨 앞에서 `-` 3개 이상, 뒤에 공백만 있는 줄이고 열린 ```` ``` ```` 펜스 밖이다. 한 줄 개행 뒤(`A⏎---⏎B`)도 경계다. `- 목록`, `␠␠---`, `--- x`, `A---`, `***`는 경계가 아니다. `~~~`는 펜스로 보지 않으므로 그 안의 `---`는 경계다. 공백은 `TranslationDocument.isBlank`와 같은 집합(NBSP 포함)이다.
- 한 규칙으로 자른다(D1). 구조 복사가 아닌 모든 요청 — 첫 요청, 빈 줄·명시 꼬리, ‘전체 다시 번역’, 제공자·방향 변경 뒤 재번역 — 은 펜스 밖 첫 경계에서 자르고, 끝의 빈 줄·구분선·치는 중인 `-`·`--`는 요청에 넣지 않는다. 나머지 블록은 기존 큐가 차례로 잇는다(한 번에 요청 하나). 원문 맨 앞의 구분선은 빈 줄이 함께 있을 때만 떼어 내 YAML 머리말(`---⏎title:`)을 보존한다. 구조 복사(원문 == 복사본) 요청은 자르지 않는다(§14).
- 경계 뒤 블록은 `isPlainText`를 보지 않는다. 그래서 A에 코드 기호가 있거나 A가 구조 복사여도 B만 요청하고 T(A)의 링크·칩이 남는다. 빈 줄 꼬리의 `isPlainText`는 prefix의 마지막 경계 뒤부터 검사한다(UTF-8 offset 하나를 prefix와 원문에 함께 쓴다).
- 구분선을 치는 모든 중간 상태는 covering 또는 planner가 받아 요청 0회, T(A) 유지다. 구분선·공백만 남은 원문은 빈 원문이다.
- 문서 대응(`reconcileInput`): covering → 문서 기준 꼬리 → 진행 중 꼬리 token 기준 → `replanned` → 전체 순서다. `replanned`는 명시 경계에서만 위 단위를 남기고 아래 블록을 다시 계획하며, 진행 중 요청은 취소한다. 그래서 완료된 B를 고치면 B′만 요청하고(T(B)는 그동안 빈다, D4), 가운데 블록 삭제(A---B---C → A---C)는 C를 `paragraph-v1` 캐시로 붙인다. 빈 줄 경계의 완료 B 편집은 지금처럼 전체다. 자동 방향에서 언어 판정이 거절한 꼬리는 다시 계획하지 않고 전체 경로로 보낸다. 위 블록은 함께 흐리게 남고, 고치지 않은 B를 따로 버리지 않는다.
- 위 블록 A만 고치면 전체 경로지만 첫 경계에서 잘려 A′만 요청하고, 이어 B는 캐시(0회) 또는 재요청이다. 그동안 이전 번역은 흐리게 두고 새 문서가 원문 전체를 덮을 때 한 번 바꾼다. ‘전체 다시 번역’도 블록마다 캐시를 우회한다.
- 결과 창: 단위 사이에 1pt `separatorColor` 선을 그린다. 저장소 문자열에 아무것도 더하지 않아 ⌘C·드래그·Services·복사 버튼·삽입은 `T(A)⏎⏎T(B)`다. 원문 창: 경계로 인정된 줄은 대시를 숨기고(TextKit 2 rendering attribute) 마크다운 가로줄처럼 컨테이너 폭 전체에 같은 선 하나만 긋는다(2026-10-13 사용자 피드백으로 회색 대시+가는 선에서 바꿈). 글자는 바뀌지 않는다.
- ⌘↩(편집 메뉴 ‘끝에 구분선 넣기’): 번역 창이 key(클릭해 활성)이면 원문 끝에 덧붙이기만 한다(진행 중 꼬리의 원문 prefix를 깨지 않는다). ⌘C 두 번으로 앞에 띄운 창은 key가 아니므로 ⌘↩는 원래 앱이 받는다. 끝의 `-`·`--`는 `---`로 채우고, 다시 눌러도 바뀌지 않는다. 내용이 없거나 열린 펜스 안이면 꺼진다.
- 자동 방향(D5): 명시 꼬리는 펜스 밖 글이 반대 지원 언어로 0.8 이상일 때만 거절한다. 측정값은 계획 문서 '구현 결과'에 있다.
