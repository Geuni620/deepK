# /create-pr

요청받은 변경을 검토 가능한 PR로 게시합니다. 이 파일은 deepK 프로젝트에서 사용하는 create-pr 스킬입니다. 사용자 작업을 보존하고 의존 관계를 명확히 하며, 로컬 검증과 원격 CI 결과를 구분합니다. 설명과 결과 보고는 한글을 기본으로 작성합니다.

## 대상과 범위 확인

- 저장소 지침과 PR 템플릿을 읽습니다. 브랜치, worktree, 스테이징 전후 변경, 커밋, 원격 저장소, upstream, 현재 브랜치의 기존 PR을 확인합니다.
- 실제 호스팅 서비스, 저장소, 기준 브랜치(base), 변경 브랜치(head)를 현재 정보로 확인합니다. GitHub, `origin`, `main`이라고 가정하지 않습니다. GitHub라면 사용 가능한 구조화된 도구나 인증된 `gh`를 우선하고, 그 외에는 해당 서비스의 도구를 사용합니다.
- PR 생성 요청에는 일반적으로 필요한 커밋 준비와 해당 브랜치의 push가 포함됩니다. PR 설명 초안이나 스킬 설치 요청은 원격 게시 권한을 뜻하지 않습니다. 머지는 사용자가 요청했을 때만 진행하되, 대화에서 이미 받은 권한도 적용합니다.
- 커밋이 필요하면 사용 가능한 `create-commit` 스킬을 활용합니다. 없다면 의도한 변경만 선택적으로 스테이징하고, 다른 작업을 보존하며, 커밋할 파일 상태를 검증한 뒤 저장소 규칙에 맞게 커밋합니다.
- PR 생성을 대신해 기준 브랜치로 직접 push하지 않습니다. 사용자가 지정한 브랜치 이름을 우선하고, 별도 지정이 없으면 새 브랜치에 `codex/` 접두사를 사용합니다.

## 검토 범위 유지

마지막 커밋만 보지 말고 기준 브랜치부터 변경 브랜치까지의 전체 diff를 확인합니다. PR의 동작에 필요한 코드, 스타일, 테스트, 문서를 함께 포함합니다.

변경 범위가 크거나 사용자가 PR 분리를 요청하면 [의존 관계가 있는 PR 나누기](references/split-prs.md)를 읽습니다. 각 PR의 목적, 기준 브랜치, 의존 관계, 검증 방법을 짧게 정리한 뒤 요청받은 작업을 진행합니다. 통상적인 묶음 결정 때문에 별도 승인을 다시 요구하지 않습니다.

커밋되지 않은 변경이 섞인 상태에서 일부를 PR로 추출할 때는 원본 checkout을 보존합니다. 각 브랜치의 실제 내용을 격리해서 검증합니다. 전체 작업 트리의 테스트 통과만으로 앞선 PR이 검증되었다고 판단하지 않습니다.

## 준비와 게시

1. 가능하면 관련 원격 참조를 갱신하고 기준 브랜치를 확인한 뒤, 전체 diff에 의도하지 않은 변경이 없는지 살핍니다. 원격 상태를 확인할 수 없다면 오래된 정보를 최신이라고 표현하지 말고 한계를 알립니다.
2. 게시할 정확한 브랜치 리비전에서 필요한 검사를 실행합니다. 범위 안의 실패는 해결하고 남은 제약은 정확하게 설명합니다.
3. 최종 변경을 기준으로 제목과 본문을 작성합니다. 저장소 템플릿을 따르고, 구체적인 문제와 변경 후 동작을 먼저 설명한 뒤 검증 결과와 의존 관계를 적습니다. 작은 PR은 작업 목록을 늘어놓기보다 짧게 설명합니다. 저장소의 명시적인 언어 규칙이나 사용자 지정이 없다면 제목과 본문도 한글로 작성합니다.
4. 확인한 원격 저장소에 의도한 브랜치만 push합니다. 기존 권한이 해당 브랜치의 이력 재작성을 명시적으로 포함하지 않으면 강제 push하지 않습니다. 허용된 경우에도 현재 원격 head를 확인하고 `--force-with-lease`를 사용합니다.
5. PR을 생성하거나 같은 head/base의 기존 PR을 수정합니다. 사용자가 요청했거나 미해결 의존성·검증 문제로 아직 검토 준비가 되지 않았다면 draft로 만들고 이유를 설명합니다.
6. 여러 줄 본문은 구조화된 도구 인자로 전달합니다. `gh`를 사용할 때는 본문을 임시 파일에 그대로 쓰고 `--body-file`로 전달합니다. 설명 문자열을 셸 코드에 직접 끼워 넣지 않습니다.
7. 생성 후 PR URL, base/head, draft 상태, 변경 파일 요약을 다시 확인합니다. PR 링크, 범위, 검사 결과, 남은 의존성을 보고합니다. 원격 근거 없이 리뷰 승인이나 CI 성공을 주장하지 않습니다.

push나 PR 생성 결과가 불확실하면 재시도 전에 원격 브랜치와 기존 PR을 확인합니다. 중복 PR을 만들거나 바뀌지 않은 상태를 반복 조회하지 않습니다.

## 머지까지 요청된 경우

- PR 상태, 현재 head SHA, base, 머지 가능 여부, 필수 검사와 리뷰 조건을 다시 확인합니다. 검사는 현재 head에 대한 결과여야 하며 이전 실행의 성공을 근거로 삼지 않습니다.
- 호스팅 서비스와 저장소의 머지 조건을 충족합니다. 브랜치 보호, 필수 리뷰, 실패한 검사를 우회하지 않습니다. 저장소가 허용하는 머지 방식이나 사용자의 명시적 선택을 따릅니다. 사용자가 요청한 커밋 구성을 알리지 않고 squash하지 않습니다.
- 대기 중 base나 head가 바뀌면 diff와 검사 결과를 다시 평가합니다. 확인 시간을 제한하고 조회 간격을 점차 늘리며 의미 있는 변화만 보고합니다. 외부 승인이나 CI가 계속 대기 중이면 무기한 기다리거나 머지했다고 주장하지 말고 차단 원인을 알립니다.
- 기존 권한 범위에서 머지하고 원격의 머지 상태와 결과 커밋을 확인합니다. 의존 PR은 다음 PR로 넘어가기 전에 PR 분리 참고 문서의 절차를 따릅니다.
- 브랜치 삭제와 정리는 머지와 별개입니다. 사용자 작업이 있는 checkout이나 다른 PR이 사용하는 브랜치를 제거하지 않습니다. 정리를 허가받았거나 이미 합의한 저장소 절차에 포함된 경우에만 진행합니다.

PR 생성·수정, 검사 대기·통과, 머지 완료·차단 여부와 남은 작업을 실제 결과대로 보고합니다. 머지까지 요청받았다면 PR 생성만으로 작업이 끝났다고 판단하지 않습니다.

## deepK 프로젝트 기준

- 소스 변경은 작업 브랜치에서 수행하고 PR을 통해 main에 병합합니다. main에 직접 커밋하거나 푸시하지 않습니다. 선행 PR이 있으면 중간 base와 최종 main 병합 경로를 명시합니다.
- 사용자는 TypeScript 경험이 있지만 Swift 소스를 읽는 데 익숙하지 않습니다. 파일명과 API 나열보다 사용자의 행동, 변경 전후 결과, 지금 사용할 수 있는 기능을 먼저 설명합니다.
- 줄 수보다 하나의 목적과 검증 가능한 결과로 PR을 나눕니다. 예를 들어 프로젝트 설정, 기본 화면, 번역 연결, Mac 연동을 구분할 수 있지만 고정 순서로 강제하지 않습니다.
- 기반 작업에는 사용자 기능이 아직 없음을 밝히고, 예시 응답과 실제 번역 연결을 구분합니다.

## 이해하기 쉬운 설명과 화면 증거

PR 제목은 작업의 구체적인 결과를 나타낸다. 본문은 변경 규모에 맞게 아래 내용을 담고 빈 형식적 항목은 만들지 않는다.

- 목적: 어떤 필요나 문제를 해결하는가.
- 변경 내용: 이전과 이후에 무엇이 달라지는가. 기능 작업은 구체적인 사용 흐름으로 설명한다.
- 사용 가능한 범위: 사용자가 지금 할 수 있는 일과 예시·모의 응답인지 실제 연결인지.
- 화면: 화면 변경에는 해당 버전의 실제 실행 스크린샷과 설명을 포함한다. 전후 비교가 유용하면 같은 조건으로 비교한다. 새 화면은 이후 화면만으로 충분하다.
- 검증: 수행한 빌드와 의미 있는 동작 확인, 결과, 확인하지 못한 범위를 기록한다. 빌드 성공을 실제 앱 간 연동이나 성능 검증으로 대체하지 않는다.
- 남은 작업: 이번 PR에 포함하지 않은 기능과 관련 후속 PR이 있다면 그 관계.

디자인 시안이나 생성 이미지를 실행 증거로 제시하지 않는다. 화면 변화가 없는 설정·문서 작업에는 불필요한 스크린샷 대신 설정의 역할과 검증 결과를 설명한다. 스크린샷에는 해당 기능에 필요한 영역만 담고 계정 정보나 개인 텍스트가 노출되지 않게 한다.

GitHub PR에 로컬 파일 경로만 넣어서는 다른 사람이 화면을 볼 수 없다. 현재 환경에서 지원하는 첨부 방식이나 접근 가능한 저장소 자산을 사용하고 접근성을 확인한다. 첨부 수단 또는 실행 환경이 없으면 로컬 산출물과 제한을 명시하며 첨부 완료라고 하지 않는다. 무관한 외부 이미지 호스팅에 업로드하지 않는다.

PR을 생성하거나 수정한 뒤 실제 diff와 설명의 범위가 일치하는지 확인한다. Codex의 PR 연결 도구를 사용할 수 있으면 작업에 PR을 연결한다.

## 테스트 실행 범위와 속도·성능 보고

2026-10-17 사용자 요청: PR에서 실제로 돌린 검사 규모와 속도·성능의 변경 전후를 확인할 수 있게 한다. 기존 테스트 통과와 실제 복사 포맷의 검증 범위를 구분한다.

- PR 검증에 실행 명령, 검사한 head/base SHA, 전체 테스트 실행 횟수와 변경 관련 회귀 사례, 실패·재실행을 기록한다. 테스트 파일 수·실행 프로그램 수·단언문 수를 개별 케이스 수처럼 쓰지 않는다. 2026-10-17 포맷 회귀 검사 추가 후 `scripts/test.sh`는 29개 테스트 파일을 25개 프로그램으로 실행한다. 포맷 검사의 `XFAIL`(미해결)은 통과 수와 구분하고 `--strict` 결과도 기록한다. 이후에는 해당 리비전의 실제 구성을 기준으로 적는다.
- PR 본문에 속도·성능 변화를 기록한다. 문서만 바꿨다면 영향 대상이 없다는 근거를 짧게 쓰고, 실행 경로를 바꿨는데 측정하지 못했다면 `미측정`과 이유·남은 확인을 적는다. 미측정을 `변화 없음`이나 `0%`로 표시하지 않는다.
- 성능에 영향을 주는 변경은 기준 base와 최종 head를 같은 입력·분량·환경·빌드 설정으로 비교한다. 제공자·모델·Fast 계층·캐시 적중 여부·대기 프로세스/스레드 준비 상태가 다르면 별도 조건이다. 실제 앱 전체 지연과 엔진 호출 시간도 구분한다.
- 바뀐 경로에 맞는 지표를 고른다. 번역은 첫 응답/최종 완료 시간과 요청 수·입력량, 가져오기·표시는 처리/레이아웃 시간, 메모리 관련 변경은 메모리 사용량을 본다. 해당 없는 지표를 채우려고 무관한 벤치마크를 돌리지 않는다.
- 비교 결과는 `지표 | 변경 전 | 변경 후 | 차이 | 표본·반복 수/조건`으로 적고 단위를 붙인다. 합성 표본·실제 입력 여부, 실패 수와 숫자·코드·링크·목록의 보존 결과, 원본 결과를 확인할 수 있는 저장소 경로나 접근 가능한 근거도 남긴다. 품질이 깨진 결과를 속도 개선의 성공 사례로 세지 않는다.
- 구독 사용량이 적다는 사용자 제약을 따른다. 먼저 로컬 회귀 테스트·가짜 제공자·저장된 응답으로 검사하고, 실제 모델 비교는 승인 범위 안에서 해당 변경의 대표 표본과 제한된 호출 수로 진행한다. 계획한 호출 상한과 재시도를 포함한 실제 호출 수를 기록하며, 모든 모델·제공자로 자동 확장하지 않는다. Claude 서브에이전트의 위임 횟수와 사용량(확인 가능한 범위)은 번역 요청과 별도로 기록한다.
- 표본이 적으면 개별 측정값·범위와 표본 수를 보여 준다. 작은 표본으로 p95나 일반적인 속도 향상을 주장하지 않는다. 검증 뒤 코드나 base가 바뀌면 기존 비교가 유효한지 확인하고, 영향을 받은 검사와 측정만 갱신한다.

## 실제 사용으로 개선하기

사용자가 이 스킬의 지속 개선을 요청한 범위에서, 실제 PR 피드백이나 관찰된 문제를 근거로 좁게 수정한다. 가상의 실패를 근거로 규칙을 계속 추가하지 않는다.

다음 관점으로 확인한다: PR 크기와 의존 관계, 비개발자도 이해할 수 있는 설명, 스크린샷의 유용성, 실제 검증과 미완성 범위의 구분.

스킬 수정은 별도 브랜치 또는 관련 작업 브랜치의 명확한 커밋으로 분리해 검토 가능하게 한다. 변경 설명에 관찰된 문제 또는 사용자 피드백, 수정한 규칙, 다음 PR에서 확인할 결과를 기록한다. 이후 실제 적용 결과로 유지·수정·삭제를 판단한다. 사례 하나의 취향을 모든 작업의 의무로 확대하지 않는다.

이 파일을 기준으로 직접 개선하며 동일한 규칙을 여러 문서에 복제하지 않는다. 실제 사례가 쌓여 별도 참고 자료가 유용해질 때만 추가한다. 초기 버전의 문서 검증과 실제 PR을 통한 효과 검증을 구분한다.
