# 의존 관계가 있는 PR 나누기

사용자가 검토할 변경량을 줄이거나, 변경을 순서대로 PR로 올리고 머지하길 요청할 때 읽습니다.

## 실제 diff로 계획하기

목적, 변경 영역, 기준 브랜치, 의존 관계, 검증 방법을 짧은 표로 정리합니다. 임의의 줄 수보다 검토 주제와 배포 가능한 동작을 기준으로 나눕니다. 코드와 필수 스타일은 함께 묶습니다.

예를 들어 데스크톱 앱의 변경은 다음 순서로 나눌 수 있습니다.

1. 실행 가능한 UI와 데스크톱 IPC 기반 구현
2. 동작을 유지하면서 컴포넌트와 CSS의 소유 범위를 나누는 리팩터링
3. 디자인과 상호작용 변경

이는 예시이며 반드시 PR 세 개를 만들라는 뜻이 아닙니다. 실제 변경으로 일관된 중간 파일 상태를 만들 수 있을 때만 나눕니다. 최종 작업 트리에 과거 상태가 남아 있지 않으면 중간 상태를 의도적으로 재구성·검증하거나, 실제로 성립하는 더 적은 수의 PR로 묶습니다. 현재 파일을 모두 첫 PR에 넣고 빈 후속 PR을 만드는 것은 분리가 아닙니다.

변경을 추출하기 전에 원본 HEAD, index, 추적되지 않은 파일, 작업 diff를 기록합니다. 원본 작업은 해당 checkout에 보존합니다. 필요하면 별도 worktree·브랜치와 명시적인 패치를 사용합니다. 저장한 패치를 다른 기준 브랜치에 무조건 적용하거나, 그사이에 사용자가 바꾼 내용을 덮어쓰지 않습니다.

## PR 연결 방식 선택

- **독립 PR:** 각 브랜치는 확인된 기준 브랜치에서 시작하고 다른 PR에 의존하지 않습니다.
- **순차 PR:** 하나를 올리고 머지한 뒤 다음 작업을 진행하도록 요청받았을 때 적합합니다. 첫 브랜치를 검증·게시하고, 권한이 있으면 머지한 뒤 기준 브랜치를 갱신합니다. 다음 diff는 머지된 기준에서 구성하고 검증합니다.
- **쌓인 PR:** 서로 의존하는 작업을 동시에 검토해야 할 때 적합합니다. PR B의 기준은 PR A의 브랜치, PR C의 기준은 PR B의 브랜치로 둡니다. 본문에 관계를 명시하고 호스팅 서비스가 필요한 기준 브랜치 변경을 지원하는지 확인합니다.

사용자의 선호 흐름을 따릅니다. 별도 지정이 없다면 가능한 변경은 독립 PR로 나누고, 순차 머지를 명시적으로 요청받았다면 순차 PR을 우선합니다. 의존 관계를 단순하게 만들 목적으로 머지 권한을 가정하지 않습니다.

## 각 분리 경계 검증

각 브랜치에서 base부터 head까지의 전체 diff와 필수 파일을 확인하고, 해당 브랜치만으로 필요한 검사를 실행합니다. 앞선 PR에 뒤의 디자인·동작 변경이 섞이지 않았는지 확인합니다. 리팩터링 PR은 앞 PR의 동작과 외형을 유지해야 하며, 관련 테스트나 UI 검사로 그 주장을 검증합니다.

## 앞선 PR이 머지된 뒤

후속 PR의 기준을 변경하기 전에 실제 머지된 기준 브랜치를 갱신합니다. squash나 rebase 방식으로 머지하면 커밋 식별자가 바뀔 수 있습니다. 이때 파일 내용이 맞아 보여도 후속 브랜치의 diff에 앞선 변경이 중복 표시될 수 있습니다.

커밋의 조상 관계와 전체 diff를 비교합니다. 필요하면 머지된 기준에서 새 브랜치를 만들고 남은 후속 변경만 적용합니다. 이미 게시한 브랜치를 수정하려면 이력 재작성이 필요한 경우, 자동으로 강제 push하지 말고 기존 권한 범위를 따릅니다. 자동으로 기준 브랜치가 바뀐 PR도 base와 diff를 다시 확인합니다. 자동 변경만으로 의존 관계가 올바르게 정리되었다고 판단하지 않습니다.

의미 있는 rebase, 충돌 해결, 기준 변경 뒤에는 필요한 검사를 다시 실행합니다. 다음 PR의 현재 head가 저장소 조건을 충족한 뒤 머지합니다. 각 PR의 URL과 머지 완료·대기 상태를 구분해 보고합니다.
